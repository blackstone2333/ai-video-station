# 刮削功能是否应该进入 AI Video Station

## 结论

值得做，但建议作为可插拔的元数据增强模块，而不是下载、命名、硬链接的强制依赖。

AI Video Station 当前的价值在于链路短：识别资源页与链接名称，规范化文件，然后用硬链接入库。完整刮削一旦进入同步主链路，外部 API 抖动或匹配错误就会阻塞本来可以正常完成的下载。因此第一阶段应该保持核心可离线运行，刮削失败不影响入库。

## 能解决的问题

- 用 TMDB、TVDB、Douban 或 Bangumi 补全正式中文标题、原始标题和年份
- 为电视剧/动漫补齐 Season、Episode 和集标题
- 生成 Emby 可读取的 NFO、海报、背景图和演员信息
- 处理资源页只写缩写、拼音首字母或版权规避名称时的歧义
- 用外部 ID 保持重命名和媒体库识别的一致性

## 代价与风险

- 需要管理不同服务的 API Key、代理、区域与语言偏好
- 同名重拍、年份缺失、特别篇、合集和动画季序会产生错误匹配
- 不同数据源的季集顺序可能不一致，尤其是动漫绝对集数与电视季编号
- 远程限流和网络故障会增加下载后处理延迟
- 海报与元数据会引入额外写入、缓存、更新和版权边界
- 错误刮削后自动重命名的破坏性远高于“少刮一张海报”

## 推荐架构

1. 定义 `MetadataProvider` 接口，TMDB、Bangumi 等各自实现适配器。
2. 输入使用资源页标题、链接名称、年份、媒体类型和季集证据；输出统一候选模型与置信度。
3. 高置信度结果只补充缺失字段，不覆盖用户明确输入。
4. 中低置信度进入后台待确认队列，不自动更改已经入库的文件。
5. 元数据结果按 provider ID 缓存，设置 TTL，避免重复请求和触发限流。
6. 命名计划保存 external ID 与采用的元数据快照，保证审计和可重试。
7. NFO/图片在硬链接成功后异步生成；失败只记录告警，不回滚硬链接。

## 建议迭代顺序

- 第一期：TMDB 电影/剧集标题、原始标题、年份与 external ID，只做预览和人工确认
- 第二期：电视剧集标题与 NFO，增加置信度阈值和候选选择页
- 第三期：Bangumi 动漫季序与绝对集数映射
- 第四期：海报/背景图下载、定期刷新和媒体库通知

在这套边界下，刮削会提升 Emby 识别率，但不会把轻量下载整理工具演变成另一个难以维护的完整媒体服务器。
